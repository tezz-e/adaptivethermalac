# 2\. Project Title

Adaptive Thermal Comfort Advisory & Control System for Campus Hostels and Classrooms

# 3\. Problem Statement

Most hostel AC units have no thermostat — they're either fully on or fully off, with no way to set a target temperature. Left running overnight, rooms often get uncomfortably cold, since a fixed cooling load doesn't account for lower nighttime metabolic rate or the extra insulation of sleepwear and blankets. Residents cope by just switching the AC off, or leaving it on and using extra blankets instead of the room being comfortable on its own.

Classrooms have a related but different problem: centralized cooling runs on a fixed schedule regardless of occupancy, time of day, or actual outdoor conditions. Neither hostel residents nor classroom occupants have any way to flag a mismatch back to the system, and facilities staff have no data to justify adjusting fixed schedules beyond anecdotal complaints.

# 4\. Proposed Solution

The system has two parts built on a shared comfort model.

* **Recommendation engine (software):** Live outdoor weather data (OpenWeatherMap) feeds the ASHRAE Adaptive Comfort Model, which computes a comfort temperature band adjusted for room type (hostel vs. classroom) and time of day. This is the shared backend logic for both parts below.

* **Hostel unit (hardware):** since hostel ACs are on/off only with no thermostat, the system acts directly rather than only displaying a recommendation. An ESP32 with a DHT11 sensor reads room temperature and sends it to the backend; the backend compares it against the current comfort band (with a hysteresis buffer to avoid rapid switching) and returns an on/off decision; the ESP32 actuates a servo mounted on the physical AC switch. A small display on the unit shows the live reading and current state.

* **Classroom dashboard (software only):** classroom occupancy isn't practical to instrument for this project, so this half stays advisory — a Streamlit dashboard for facilities staff showing the recommended vs. current fixed setpoint and flagging mismatches.

# 5\. Practical Utility & Novelty

For hostels specifically, the hardware unit is what makes the recommendation actionable: since there's no thermostat, residents have no way to act on a suggested setpoint in real time, especially overnight. Automating the response — switching the AC off once conditions are within the comfortable band — turns the comfort model into an outcome rather than just a data point.

For classrooms, the value is different: converting scattered complaints (“the AC is too cold in here”) into a quantified, time-stamped recommendation facilities staff can act on.

Most existing smart-thermostat products (Nest, Ecobee) assume individually controllable HVAC with native scheduling. Our constraint is the opposite — centralized, binary (on/off) hostel units and fixed-schedule classroom systems — so the software has to work around hardware limitations rather than replace a thermostat that already exists.

# 6\. Proposed Methodology

* **1\. Data acquisition:** outdoor temperature/humidity from a weather API (Vellore); room temperature from the ESP32 \+ DHT11 for the hostel unit; simulated occupancy, clothing insulation, and metabolic rate parameters for classrooms (no sensors there).

* **2\. Processing:** ASHRAE Adaptive Comfort Model implemented in Python, computing a comfort band per room type and time of day.

* **3\. Decision logic:** hostel — sensor reading vs. comfort band, with a hysteresis buffer, produces an on/off decision sent to the ESP32 for servo actuation. Classroom — comfort band vs. fixed setpoint produces a flagged mismatch shown on the dashboard.

* **4\. Output:** a Streamlit dashboard (24-hour recommended band, current vs. recommended temperature, mismatch flags, exportable summary) plus an on-device display for the hostel unit (live temperature, target band, AC state).

# 10\. Expected Outcomes

A working Python system that: (1) fetches live outdoor weather data for the campus location; (2) computes a recommended AC setpoint band for hostel rooms and classrooms separately using the ASHRAE Adaptive Comfort Model; (3) for hostels, automatically switches the AC on/off through the ESP32 \+ servo unit based on that recommendation; (4) for classrooms, compares recommendations against fixed institutional setpoints and flags mismatches on a dashboard. The final deliverable is a working prototype (software \+ hardware unit) with a short report covering model assumptions and sample outputs.

# 14\. Existing Solutions / References

The project draws on the ASHRAE 55 Adaptive Comfort Standard and existing smart-thermostat systems such as Nest and Ecobee, which use adaptive scheduling for individually controllable home HVAC. This project differs by targeting centralized, binary (on/off) institutional systems — generating an advisory dashboard for classrooms, and closing the loop with direct hardware actuation for hostel units where no thermostat exists.
